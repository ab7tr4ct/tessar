## E1. Мини-набор: формы слов, синонимы, другой язык

**Зачем.** Быстро понять, закрывают ли векторы слабые места нашего BM25
(морфология, синонимы, межъязыковой поиск).

**Постановка.** 16 фактов (рус/англ) и 16 вопросов, написанных вручную
под слабые места: формы слов («журналы» → «журнал»), синонимы
(«ограничения» → «лимит»), другой язык («куда переехала Аня?» → «Anna moved
to Berlin»), точные строки (`TS-999`, `src/main.rs`, HGVL). Вопросы писал
я — набор подыгрывает, это ориентир, а не замер.

**Результат.**

| Модель | top-1 | top-3 | MRR |
|---|---|---|---|
| BM25 tessar | 9/16 | 10/16 | 0.59 |
| multilingual-e5-small | 13/16 | 15/16 | 0.89 |
| EmbeddingGemma v1 | 16/16 | 16/16 | 1.00 |

**Вывод.** BM25 проваливает формы слов и межъязыковые вопросы, точные
строки находит. Векторы закрывают провалы. Стеммер (Snowball) проверяли
отдельно: помогает частично и ошибается («журнал» → «журна», но
«журнале» → «журнал»). Решение: свою морфологию не строим, векторы
переносим на M2.

## E2. Локальные модели: LongMemEval 30 + RuBQ

**Постановка.**
- LongMemEval S, 30 вопросов (по 5 на тип, без abstention), данные из
  cortex-db (`eval/data/raw/longmemeval_s_cleaned.json`); единица поиска —
  пара реплик (пользователь + ассистент), до 1500 символов; ~250 единиц на
  вопрос, 7558 всего. Метрики: hit@5, hit@10, recall@10 (доля реплик
  с ответом в top-10), MRR.
- RuBQ (`ai-forever/rubq-retrieval`), 150 русских вопросов + ~2,1 тыс.
  отвлекающих абзацев Википедии (2279 документов).
- Запуск: ONNX Runtime на CPU (`fastembed` / `ort`) и llama.cpp + Metal
  (GGUF Q8, релиз b12189).

**Результат.**

| Модель | Где | LME hit@5 | LME hit@10 | LME recall@10 | LME MRR | RuBQ hit@1 | RuBQ MRR | Вектор |
|---|---|---|---|---|---|---|---|---|
| BM25 tessar | CPU | 73% | 87% | 70% | 0.61 | 49% | 0.59 | — |
| multilingual-e5-small | CPU | 90% | 97% | 85% | 0.73 | 94% | 0.96 | 384 |
| EmbeddingGemma v1 | GPU | 83% | 93% | 88% | 0.76 | 95% | 0.97 | 768 |
| EmbeddingGemma 2 | GPU | 90% | 90% | 83% | 0.75 | 95% | 0.97 | 768 |
| voyage-4-nano | GPU | 87% | 97% | 90% | 0.75 | 93% | 0.96 | 2048 |

Скорость (RuBQ, мс на документ): Gemma v1 — 68 на CPU против 13 на GPU;
voyage-nano (4 бит) — 151 на CPU против 25 на GPU. Запрос на GPU через
llama-server — 12–17 мс.

**Вывод.** Векторы далеко впереди BM25. Различия между векторными
моделями — 1–2 вопроса из 30 (шум). RuBQ слишком лёгкий (все 93–95%).
GPU ускоряет в 5–6 раз.

**Попутно.**
- ONNX Runtime на macOS по умолчанию выбирает CoreML — он оказался
  в разы медленнее CPU (e5: >18 мин против 6). В продукте явно включать CPU.
- Сортировка текстов по длине перед пачками снижает выравнивание пустыми
  токенами.
- EmbeddingGemma 2 в ONNX требует пустые входы для картинок, аудио, видео.
- llama-server: для пачек нужны параллельные слоты (`--parallel`), иначе
  тексты идут по одному; контекст слота должен вмещать самый длинный текст.

## E5. Датасет memory-bench из своих заметок

**Зачем.** LongMemEval — английские диалоги одного человека; наш случай —
глобальная память по многим проектам, вопросы по-русски к английским
заметкам, ответы, зависящие от проекта.

**Как собран.**
1. Корпус: 147 файлов памяти Claude Code из 46 проектов
   (`~/.claude/projects/*/memory/*.md`), 105 англ / 27 рус / 15 смешанных.
2. Очистка (`redact.py`, воспроизводимо из исходников, те же id):
   секреты, email, IP, телефоны, id деплоев и аккаунтов, логины,
   `user@host`, «неугадываемые» пути; даты сохранены. 18 заметок
   затронуто. Исходные файлы не меняются.
3. 5 агентов писали вопросы по частям корпуса (сгруппированы по
   проектам): прямые, перефразированные, межъязыковые, «без проекта»,
   по нескольким заметкам, без ответа.
4. 3 агента-проверяющих видели весь корпус: правили ответы, добавляли
   заметки из других проектов (`also_relevant`), ставили `asked_from`
   и `ambiguous`, проверяли «без ответа» по всему корпусу.
5. Сборка: убраны 8 дублей между частями, 8 вопросов о личной жизни
   помечены `private` (не публиковать).

**Итог:** 422 вопроса — прямые 126, межъязыковые 113, перефразированные 84,
«без проекта» 65, по нескольким заметкам 17, без ответа 17; рус 202 /
англ 220; 28 неоднозначных без контекста проекта; 130 с подходящими
заметками в других проектах; 29 исправлено проверкой, 0 удалено.

**Что нашли по пути.** Противоречия между проектами (стиль коммитов,
Co-Authored-By, пакетный менеджер); устаревание — новая заметка, иногда
из другого проекта, перекрывает старую; заметки gobopro продублированы
под двумя проектами; сканер секретов сначала резал даты как телефоны —
исправлено.

## E6. memory-bench: модели и границы пространств

**Постановка.** Корпус — 147 заметок, 405 вопросов с ответом. Режимы:
вся память; мягкий бонус к сходству для заметок проекта `asked_from`
(+0.02 / +0.05 / +0.10); жёсткая стена (только свой проект).

**Вся память:**

| Модель | hit@1 | hit@5 | MRR | Межъязыковые hit@1 | Рус / англ hit@1 |
|---|---|---|---|---|---|
| BM25 tessar | 43% | 63% | 0.53 | 16% | 29% / 57% |
| voyage-4-nano @2048 | 74% | 92% | 0.82 | 67% | 70% / 78% |
| voyage-4-nano @1024 | 74% | 92% | 0.82 | 67% | 70% / 78% |
| voyage-4-large (API) | 78% | 96% | 0.86 | 73% | 75% / 80% |

**С контекстом проекта (hit@1 / MRR; неоднозначные — hit@1):**

| Режим | nano @1024 | large | Неоднозначные (28): nano / large |
|---|---|---|---|
| вся память | 74% / 0.82 | 78% / 0.86 | 39% / 46% |
| бонус +0.05 | 84% / 0.89 | 86% / 0.91 | 64% / 75% |
| бонус +0.10 | 87% / 0.91 | 90% / 0.94 | 68% / 82% |
| жёсткая стена | 88% / 0.92 | 91% / 0.94 | 82% / 93% |

«Не знаю» по сходству лучшего результата: AUC ~0.75 (nano и large).

BM25: аддитивный бонус к его баллам не имеет смысла (шкала другая) —
почти ничего не меняет; жёсткая стена поднимает до 70% hit@1. Для
слияния с BM25 бонус пространства надо задавать на уровне мест (RRF),
а не баллов.

**Выводы.**
1. Контекст проекта даёт больше, чем выбор модели: +10–14 п.п. hit@1 против
   2–4 п.п. между nano и large.
2. Без векторов на этих данных нельзя: BM25 на межъязыковых — 16%.
3. Жёсткая стена выглядит лучшей только потому, что в датасете нет
   вопросов «из проекта A про проект B» — на них стена проваливается.
   Величину бонуса подбирать на таких вопросах (E7).
4. Для честного «этого нет в памяти» одной оценки сходства мало — нужен
   переранжировщик или проверка моделью.

## E7. Межпроектные вопросы: величина бонуса пространства

**Зачем.** В E6 жёсткая стена выглядела лучшей, потому что все вопросы
задавались из проекта, где лежит ответ. Нужны вопросы «из проекта A про
проект B», чтобы подобрать бонус, который помогает своему проекту и не
прячет чужой.

**Постановка.** Два агента прочитали весь корпус и написали 80 вопросов
(`evals/memory-bench/cross.jsonl`, по 10 рус и 10 англ в каждом виде):
- `cross_project_named` (20) — вопрос называет другой проект;
- `cross_project_implicit` (20) — проект не назван, но есть деталь,
  которая встречается только в нём (`jev-router`, Railway, `sendWidget`…);
  `asked_from` часто выбран с похожей заметкой-ловушкой (вопрос про bun —
  из проекта на pnpm);
- `user_wide` (20) — общий факт о пользователе, заданный из любого проекта;
- `multi_project` (20) — ответ собран из нескольких проектов (до 7 заметок).

Независимым агентом не проверялись (`status: unverified`); проверил
формат, ссылки на заметки, что `asked_from` ≠ проект ответа, утечки.
Прогон: 422 + 80 вопросов, 485 с ответом. Подмножества: «свой» — хотя бы
одна заметка ответа в `asked_from` (370), «чужой» — ни одной (76),
без проекта — 39. Бонусы: 0 / 0.02 / 0.03 / 0.05 / 0.07 / 0.10 / 0.15
к косинусу, жёсткая стена.

**Результат, hit@1 (свой / чужой / все):**

| Режим | nano @1024 | voyage-4-large | BM25 |
|---|---|---|---|
| вся память | 75 / 83 / 75 | 78 / 89 / 79 | 45 / 49 / 44 |
| бонус +0.03 | 83 / 83 / 81 | 86 / 89 / 86 | — |
| бонус +0.05 | **86 / 83 / 84** | 88 / 86 / 86 | 47 / 47 / 45 |
| бонус +0.07 | 88 / 79 / 85 | 89 / 86 / 87 | — |
| бонус +0.10 | 89 / 75 / 85 | 91 / 80 / 88 | 47 / 47 / 46 |
| бонус +0.15 | 91 / 59 / 84 | 92 / 70 / 87 | — |
| жёсткая стена | 91 / 0 / 74 | 92 / 0 / 76 | 75 / 0 / 59 |

- hit@5 на чужих у nano — 92% при любом бонусе до +0.15: ответ из чужого
  проекта уходит с первого места, но остаётся в top-5.
- Неоднозначные (28), nano: 39% → 64% (+0.05) → 79% (+0.15) → 82% (стена).
- По видам, nano hit@1 (вся память → +0.05 → +0.10 → +0.15):
  implicit 95 → 95 → 90 → 75; named 90 → 90 → 80 → 55;
  user_wide 75 → 75 → 70 → 60; multi_project 70 → 65 → 55 → 45.
  BM25 без бонуса: implicit 65, named 60, user_wide 40, multi_project 25.
- «Не знаю», AUC: nano 0.75, large 0.76 — не изменилось.

**Выводы.**
1. **Жёсткая стена по умолчанию — нет.** На смешанном наборе она хуже
   мягкого бонуса (nano: 74% против 84%), чужие вопросы — 0%. Стена —
   только для явно закрытых пространств.
2. **Бонус по умолчанию — +0.05 для nano**: свой проект +11 п.п. (75 → 86),
   чужие без потерь на hit@1 (83 → 83). Для large бесплатный предел — +0.03.
   Дальше бонус меняет чужие ответы на свои: +0.10 — свой 89, чужой 75.
3. **Величина зависит от того, сколько результатов идёт в контекст.**
   Для автоподкладки (1–3 результата) — +0.05; для явного `recall` с top-5
   и больше можно сильнее: чужой ответ остаётся в выдаче.
4. **Первыми страдают `user_wide` и `multi_project`.** Общие факты
   о пользователе должны лежать в пространстве пользователя (вес 1.0,
   как у своего проекта), а не размазываться по проектам — тогда бонус
   их не прячет. Значит, при записи важно выбирать пространство.
5. **Прорыв по сущностям векторам здесь не нужен:** неявные вопросы nano
   находит в 95% и без бонуса, BM25 — в 65%. Но набор, скорее всего,
   лёгкий: вопросы писались с опорой на отличительную деталь.
6. Бонус — в единицах косинуса конкретной модели; при смене модели его
   надо подбирать заново или задавать через места (RRF), а не баллы.

**Оговорки.** 76 чужих вопросов (1 вопрос ≈ 1,3 п.п.), по 20 на вид
(1 вопрос = 5 п.п.). Доля чужих вопросов в реальной работе неизвестна —
итоговая колонка «все» зависит от смеси. Вопросы писали агенты, видевшие
ответ.

Логи: `evals/runs/2026-11-08/mb-cross-{nano,voyage-large,bm25}.log`,
скрипт: `evals/sandbox/scripts/mb_cross.sh`. Новых трат на API — $0.0002
(только эмбеддинги вопросов).

## E8. Канал смысла в движке и слияние каналов (H7)

**Зачем.** Проверить, что настоящий `Memory::recall` (int8, порт
`Embedder`, адаптер `llama-server`) повторяет числа песочницы, и
измерить, что дают слова и сущности поверх векторов (H7).

**Постановка.** memory-bench + межпроектные (485 вопросов с ответом).
Каждый проект — своё пространство, каждая заметка — факт `Statement`;
`near` = пространство `asked_from`, бонус 0.05. voyage-4-nano через
`llama-server`, вектор 1024 в int8. Веса каналов в RRF (k = 60):
слова и сущности (сущностей в этом корпусе нет) × w, смысл × 1.

**Результат, hit@1 / hit@5 / MRR (все; свой / чужой hit@1):**

| Вариант | Все | Свой | Чужой |
|---|---|---|---|
| только слова (BM25) | 44 / 65 / 0.54 | 44 | 49 |
| только смысл | 75 / 92 / 0.83 | 75 | 83 |
| смысл + near | **84 / 94 / 0.89** | 86 | 83 |
| всё, веса 1/1/1 | 59 / 88 / 0.71 | 59 | 68 |
| всё 1/1/1 + near | 61 / 90 / 0.73 | 61 | 68 |
| слова 0.5 + near | 65 / 94 / 0.78 | 67 | 67 |
| слова 0.3 + near | 71 / 95 / 0.81 | 73 | 67 |
| слова 0.2 + near | 75 / 95 / 0.84 | 78 | 70 |
| слова 0.1 + near | 81 / 94 / 0.87 | 83 | 78 |
| слова 0.05 + near | **84 / 94 / 0.89** | 86 | 82 |

Задержка `recall` с эмбеддингом запроса — 15–16 мс (GPU, 147 фактов);
без смысла — 2 мс. Индексация 147 заметок — 11 с (длинные тексты).

**Выводы.**
1. Движок повторяет песочницу: «только смысл» 75%, с near 84% — int8
   и путь через порт качество не теряют.
2. **H7 в простом виде не подтвердилась.** RRF с равными весами роняет
   hit@1 с 84% до 61%: RRF помнит места, а не уверенность канала, и слабое
   совпадение по словам поднимает факт выше лучшего по смыслу. Чем меньше
   вес слов, тем лучше; ни один вид вопросов от слов не выигрывает
   заметно (multi_project +5 п.п. при 0.2 — шум).
3. По умолчанию: смысл 1, слова и сущности 0.05 — слова только разбивают
   почти-ничьи. Без эмбеддера порядок от весов не меняется.
4. Оговорка: заметки длинные, BM25 на них слаб (44%). На коротких фактах
   и точных строках (id, пути, ошибки) слова могут оказаться полезнее —
   проверить на фактах, извлечённых из LongMemEval, и на коде.
5. Следующая проверка — слияние по баллам (выпуклая комбинация
   косинуса и нормированного BM25, Bruch et al., 2023) вместо мест:
   сохраняет уверенность векторов и даёт словам поднимать точные
   совпадения.

Лог: `evals/runs/2026-11-08/mb-recall-nano.log`, режим стенда `mb-recall`.

## E9. Эмбеддер в процессе: llama.cpp через свой C++-слой и `cxx`

**Зачем.** До сих пор модель жила в отдельном `llama-server`, и движок
ходил к нему по HTTP: лишний процесс, порт, запуск и отказ «сервер не
поднят». Проверить, что модель, загруженная прямо в процесс, даёт те же
векторы и то же качество, и посмотреть на скорость, память и цену сборки.

**Постановка.** Крейт `tessar-embed-llama`: llama.cpp b12189 — git
submodule, собирается статически через CMake (Metal включён, шейдеры
встроены в бинарь, `GGML_METAL_EMBED_LIBRARY`), сверху наш C++-слой
(`src/shim.cc` и `shim.h`, ~370 строк с комментариями) и мост `cxx`.
`LlamaEmbedder` реализует порт `Embedder`; модель —
`~/.tessar/models/voyage-4-nano-Q8_0.gguf`.
Настройки по умолчанию: контекст 8192 токена (самый длинный текст),
до 8 текстов в одном проходе, общий KV-буфер (`kv_unified`), все слои на
GPU. Машина — Apple M1 Pro. Сравнение — с тем же релизом `llama-server`
в прежней конфигурации (`-c 65536 -b 8192 -ub 8192 --parallel 8`).

Из GGUF выяснилось: у voyage-4-nano **двунаправленное внимание и
усреднение по токенам** (mean pooling), а не последний токен; 12 слоёв,
скрытый размер 1024, выходная проекция до 2048.

**Результат.**

1. Эквивалентность: 10 текстов (рус/англ, короткие и длинные, код) ×
   промпты документа и запроса = 20 векторов. Минимальный косинус с
   `llama-server` — **0.999999**, средний — 1.000000
   (`tests/server.rs`).
2. memory-bench через `Memory::recall` (режим стенда `mb-recall-native`):
   все строки метрик, включая разбивку по видам вопросов, **совпали
   побайтно** с прогоном через `llama-server`. Смысл + near — 84 / 94 /
   0.89 (hit@1 / hit@5 / MRR), только смысл — 75 / 92 / 0.83.
3. Скорость и память (сервер перезапущен в тот же час для честного
   сравнения):

| | `llama-server` по HTTP | в процессе |
|---|---|---|
| `recall` со смыслом + near, с эмбеддингом запроса | 14.0 мс (утром 15.1) | **12.6 мс** (повтор 13.2) |
| эмбеддинг заметки, 147 шт. одним вызовом | 72.7 мс | 73.9 мс (повтор 72.9) |
| индексация 147 заметок по одной | 10.9 с | 10.8 с |
| загрузка модели | отдельный процесс, ~1.5 с | 0.4 с (первый запуск нового бинаря — 8.3 с) |
| GPU-память: веса + KV + рабочие буферы | 351 + 3072 + 819 МБ ≈ 4.2 ГБ | 351 + 384 + 837 МБ ≈ 1.6 ГБ |

4. Подбор настроек (временные замеры, не в репозитории):
   - Длинные заметки упираются в вычисления (~8 тыс. токенов/с на M1 Pro):
     72–75 мс на заметку при 1, 4, 8 и 16 текстах на проход. Время от
     длины: 100 символов — 9 мс, 400 — 18, 1600 — 60, 6400 — 330,
     12800 — 960. В memory-bench медиана заметки 1159 символов (38 мс),
     p90 — 2831 (144 мс), самая длинная — 7415 (653 мс, 2816 токенов).
   - Короткие тексты (~15 токенов): 8.8 мс поодиночке, 4.3 по 4, **3.4
     по 8**, 4.1 по 16, 3.0 по 32 — дальше выигрыша почти нет.
   - Рабочие буферы растут на ~40 МБ за каждый текст прохода (контекст
     8192): 1 → 556 МБ, 4 → 676, 8 → 837, 16 → 1158. Настройка из
     `examples/embedding` (256 последовательностей) просит 10.4 ГБ и не
     помещается — первая версия на этом упала. Контекст 4096 при 8
     текстах — 192 МБ KV + 420 МБ буферов.
   - Веса на CPU (`Options::gpu = false`): запрос 14 мс, заметка ~260 мс
     (на GPU на тех же заметках — 51 мс).
5. Сборка: llama.cpp + слой с нуля — 32 с (124 с CPU на 10 ядрах).
   Пример-бинарь с эмбеддером — 10.8 МБ (10.2 после strip), зависит
   только от системных фреймворков и libc++.

**Что нашли по дороге.**
- Metal-бэкенд ggml при выходе из процесса проверяет, что все его буферы
  освобождены, и роняет процесс (SIGABRT), если эмбеддер ещё жив — в
  `static`, утёк или занят другим потоком при `exit()`. Слой ведёт
  список живых эмбеддеров и освобождает их обработчиком `atexit`,
  который срабатывает раньше статиков ggml; вызовы после этого
  возвращают ошибку.
- Сервер разбирает спецтокены в тексте (`parse_special`), слой — нет:
  `<|endoftext|>` в заметке остаётся текстом. На проверочных текстах
  разницы нет.
- Ошибки llama.cpp (нехватка памяти, битый файл) перехватываются из его
  лога и попадают в текст `EmbedError`; остальной лог молчит
  (`TESSAR_LLAMA_LOG=1` — показать всё).

**Выводы.**
1. Эмбеддер в процессе эквивалентен `llama-server`: те же векторы, те же
   метрики. Решение E8 и бонус near переносятся без изменений.
2. Запрос быстрее на 1.5–2 мс — это цена HTTP и JSON; остальное — сама
   модель. Индексация не меняется: она упирается в GPU.
3. GPU-памяти в 2.6 раза меньше: сервер держал 8 слотов по 8192 токена,
   нам хватает одного общего контекста.
4. Отдельный процесс больше не нужен: ни порта, ни запуска, ни отказа
   «сервер не поднят». `llama-server` остаётся по желанию — удалённая
   машина с GPU.
5. Цена: C++ и CMake в сборке (~30 с с нуля), +10 МБ к бинарю, первый
   запуск нового бинаря ~8 с (Metal компилирует шейдеры, потом кэш).
   `unsafe` — только мост `cxx` и один `unsafe impl Send` в этом крейте;
   во всём остальном workspace он по-прежнему запрещён.
6. Не мерили: машины без Metal (Linux, CUDA), сборку под Windows.

Код: `crates/embed-llama/`; тесты с моделью —
`cargo test -p tessar-embed-llama --test model -- --ignored`, сравнение
с сервером — `--test server` (нужен `TESSAR_TEST_LLAMA_SERVER`). Логи:
`evals/runs/2026-11-08/mb-recall-native.log` (в процессе),
`mb-recall-nano-rerun.log` (сервер, повтор для сравнения времени).
