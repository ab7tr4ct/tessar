# tessar — движок памяти для агентов

Версия от 2026-11-07 (до этого проект назывался graff). Предыдущие версии
документа (граф плана, оркестратор, графовая БД общего назначения) —
в истории git.

## Задача

Агент работает долго: много сессий, компактов, разговоров. Ему нужно
знать накопленное раньше: факты о пользователе и проекте, решения,
текущее состояние. Сегодня память ломается так:

| | Поломка | Пример |
|---|---|---|
| П1 | **Устаревшее значение:** отдаётся старый факт или старый и новый вместе, без пометки, какой верен | «цель проекта» за два дня менялась трижды |
| П2 | **Время:** нельзя спросить «что решили на прошлой неделе», «какой был план до X» | temporal-reasoning в LongMemEval |
| П3 | **Нужное не похоже на вопрос** | «какие там лимиты?» ← «Enterprise: 1000 rps» |
| П4 | **Сборка по многим сессиям** | «все решения про хранение данных» |
| П5 | **Цена:** память съедает контекст, запись стоит вызовов LLM | 20–40% окна после компакта; `CLAUDE.md` на 45 КБ в каждой сессии |
| П6 | **Доверие:** непонятно, почему выдано это и во что память «верит» | — |

Как ломаются существующие подходы:
- markdown-файлы — П1, П5, П6;
- векторный RAG по истории — П1–П4;
- Mem0 (LLM решает «добавить, обновить, удалить» на каждой записи) —
  П5, П6, и история стирается;
- Graphiti / Zep (факты со сроком действия, ближе всего к нам) —
  Python поверх Neo4j, противоречия определяет LLM на записи: П5
  и задержка.

Потребители по порядку:
1. **Claude Code** через MCP — первый, ежедневный, на настоящих данных.
2. **Голосовой агент** — память между звонками и состояние диалога
   в бюджете задержки голоса.
3. **Другие агенты** через сервис — потом.

## Как решаем

Память — это **структурированные факты о сущностях со сроком действия**.

- **Пишет агент**, который и так понимает контекст: сразу передаёт
  сущности и предикат. Отдельный конвейер извлечения не нужен (П5).
- **Ядро хранит историю.** Новый факт по однозначному предикату
  детерминированно закрывает старый, без LLM. По умолчанию отдаётся
  верное сейчас, прошлое — по запросу (П1, П2).
- **Поиск** по сущностям и ключевым словам; время — фильтр и бонус.
  Смысл и связи добавляются, только если замер покажет, что они чинят
  промахи (П3, П4).
- **В контекст попадают короткие факты** с объяснением, кем и почему
  найдены (П5, П6).

Отличие от Graphiti: противоречия закрываются правилом, а не суждением
LLM; запись не стоит лишних вызовов модели; ядро на Rust, встраиваемое
и быстрое.

## Гипотезы

| | Гипотеза | Что известно |
|---|---|---|
| H1 | Сроки действия и замещение дают верное текущее значение заметно чаще, чем векторный поиск по истории | не проверено; главная |
| H2 | Индекс сущностей находит нужное, но непохожее, лучше векторов при том же бюджете токенов | BABILong (синтетика): +59…+80 п.п.; на реальном тексте — нет |
| H3 | Правило по предикату не хуже LLM-решения о противоречиях (Graphiti) и в разы дешевле | не проверено |
| H4 | Окно времени и время события улучшают вопросы про время | HGVL: +7,8 п.п. на LongMemEval при 2 тыс. токенов |
| H5 | Агент сам пишет достаточно хорошие структурированные факты | не проверено; **самая рискованная** |
| H6 | Факты вместо файлов памяти в разы сокращают токены на восстановление после компакта | не проверено |
| H7 | Гибрид каналов обгоняет каждый канал отдельно; каждый канал окупается на замере с его отключением | не проверено |
| H8 | Автоматическая подкладка памяти на каждое сообщение (с порогом и бюджетом) сокращает переспрашивания, не засоряя контекст | не проверено; урок HGVL — лишний текст в контексте съедает бюджет |
| H9 | Тепло (только от полезности, с угасанием) позволяет держать горячую память ограниченной без потери качества поиска | не проверено |
| H10 | Контекстный приоритет проекта (ограниченный, сглаженный, с исследованием) улучшает автоматическую подкладку, не снижая разнообразия выдачи | не проверено |

## Проверка

**Путь А — LongMemEval** (H1–H4, H7): категории knowledge-update,
temporal-reasoning, multi-session.
- Запись: LLM проходит по сессиям «как агент» и пишет структурированные
  факты (заодно частично проверяет H5).
- Метрики: точность ответа (LLM-судья, как в LongMemEval), верность
  текущего значения, полнота при бюджете 1–2 тыс. токенов, задержка,
  цена записи.
- Базовые линии: плоский векторный top-k по репликам (стенд HGVL); вся
  история в контексте; опубликованные цифры Zep и Mem0 (осторожно:
  разные постановки).
- **Точка решения:** ≥ +5 п.п. над плоским поиском на knowledge-update
  и temporal-reasoning, интервал не задевает 0. Если нет — подход меняется
  до вложений в остальное.

**Путь Б — своё использование в Claude Code** (H5, H6): golden-набор
вопросов из реальных сессий («какая сейчас цель», «почему отказались
от X»); верность текущего значения и истории; токены после компакта;
сколько раз агент переспрашивает то, что было в памяти; токены на вызовы
`remember`.

## Принципы

1. **Ядро без LLM**, детерминированное. Извлечение и эмбеддинги — снаружи.
2. **Ничего не удаляется.** Срок действия у факта, чтение «на момент T».
3. **Точные ключи прежде векторов** (урок HGVL).
4. **Каждый результат объясним.**
5. **Пространства памяти с первого дня.**
6. **Без замеров нет фич.**

## Модель данных

| Сущность | Поля | Зачем |
|---|---|---|
| `Space` | id, имя, родитель, вид (`long_term` / `working`), состояние (открыто / архив) | граница данных; иерархия для рабочей памяти |
| `Entity` | id, тип (строка), ключ, синонимы | точка входа; ключ уникален в пространстве и типе |
| `Episode` | id, текст, время, источник | исходный текст, откуда взяты факты |
| `Fact` | id версии, `lineage`, номер версии, `prev`/`next`, вид и содержимое (`FactBody`), упомянутые сущности, эпизод, время записи, `valid_from`/`valid_to`, происхождение и уверенность, вектор (необязательно) | единица памяти; каждая версия неизменна и адресуема |

**Записи типизированы, а не произвольный JSON.** Вид факта — закрытый
`enum`; новый вид добавляется осознанно, изменением кода:

```rust
enum FactBody {
    /// «Решили не брать MongoDB».
    Statement { text: String, when: Option<TimeSpan> },
    /// (tessar, цель) = «движок памяти»; (отпуск, span) = 1–14 июля.
    Attribute { subject: EntityId, predicate: PredicateId, value: Value },
    /// (пользователь, работает_над, tessar).
    Relation { subject: EntityId, predicate: PredicateId, object: EntityId },
    /// Событие: `when` обязателен, это проверяет компилятор.
    Event { text: String, participants: Vec<EntityId>, when: TimeSpan },
}

enum Value { Text(String), Int(i64), Float(f64), Bool(bool),
             Time(Timestamp), Span(TimeSpan), Entity(EntityId) }

enum TimeSpan { Point(Timestamp), Range { start: Timestamp, end: Timestamp },
                Since(Timestamp), Until(Timestamp), Duration(Seconds) }
```

Предметные смыслы — в схеме пространства, а не в коде: типы сущностей
(`person`, `project`, `event`…) и предикаты с типом значения
и однозначностью (`define_predicate("lives_in", Entity(place), Single)`).
Запись, не подходящая под схему, отклоняется. JSON Lines в журнале — только
формат сериализации этих типов, его можно заменить на бинарный.

**Как хранится граф.** Без указателей и связных списков: записи лежат
в векторах, id — номер в векторе (доступ O(1)), связи — числа. Сущность →
её факты: `Vec<Vec<FactId>>` по номеру сущности; `prev`/`next` у версий —
тоже числа. Компактный CSR (как в HGVL) — только для неизменяемых снимков
под алгоритмы обхода, если до них дойдёт. Движок обхода графа (PPR,
многошаговые пути) отложен до замеров.

**Правило обновления.** Если у факта есть `(subject, predicate)`
и предикат объявлен однозначным в схеме пространства, новый факт с той
же парой становится его новой версией (`valid_to` и `next` у старой). Факты без
структуры закрываются явно через `update`.

**Происхождение:** `asserted` (человек, агент, хук) или `inferred`
(модель, алгоритм) с уверенностью. Выведенное — гипотеза, пока не
подтверждено.

## Время

Время — метаданные факта, а не узел графа. Три поля:
- **время записи** — когда память узнала факт (совпадает с порядком журнала);
- **срок действия** (`valid_from`/`valid_to`) — когда утверждение верно;
  закрывается обновлением;
- **`when`** (необязательно) — когда описанное происходит в мире.

`when` — это `TimeSpan`: точка, интервал, открытый интервал («с марта»)
или только длительность («две недели», даты неизвестны). Неточная дата —
интервал по точности: «в марте» = [1 марта, 1 апреля).

Пример: 20 июня записано «отпуск 1–14 июля». Срок действия — с 20 июня,
`when` — 1–14 июля. В июне отпуск перенесли на август — новая версия
факта; старая закрыта, но остаётся в истории.

Три вопроса: «что было верно на момент T», «что память знала на момент
T», «что происходило в период P».

Названные периоды и события («релиз 1.0», «отпуск», «Q3») — сущности
типа `event`/`period`. Их интервал — факт `Attribute` с предикатом `span`
и значением `Value::Span`, поэтому он версионируется так же, как всё
остальное.

Индексы времени почти бесплатны:

| Что нужно | Как | Цена |
|---|---|---|
| порядок по времени записи | факты и так дописываются по порядку → двоичный поиск | 0 байт |
| история сущности | список фактов сущности дописывается по порядку → уже хронологический | 0 байт |
| «верно сейчас» | битовая карта действующих фактов; замещение переключает бит | 1 бит на факт |
| `as_of` и бонус за окно | проверка интервала только у кандидатов из каналов (десятки–сотни) | 0 байт |
| запрос только по времени («что было на прошлой неделе») | отсортированный массив (начало `when`, id) | 16 байт на факт; вставка не по порядку — сдвиг массива, ~0,1 мс на 100 тыс. фактов |

Последний индекс строится, когда появится такой запрос.

## Версии

Каждое изменение факта — новая неизменная версия со своим id. Версии
одного факта образуют цепочку: `lineage` (id первой версии), номер
версии, `prev` и `next` — прямые ссылки назад и вперёд. Индекс
`lineage → последняя версия` даёт текущее значение за O(1).

Ссылки на факт — как в git:
- **на `lineage`** — как на ветку: всегда текущая версия;
- **на id версии** — как на коммит: ровно та версия, навсегда.

Два вида новой версии (`update` с причиной):
- **изменение** — мир поменялся («переехал в Берлин»): старая версия
  была верна до момента изменения;
- **исправление** — старая была ошибкой («не Москва, а Минск»): в ответах
  «что было верно на момент T» она больше не участвует, в «что память
  знала на момент T» — остаётся.

Сущность — это идентичность (id, тип, ключ, синонимы). Всё, что о ней
известно, включая интервал события, — факты, поэтому версии устроены
одинаково для всего. Изменения синонимов есть в журнале, и `as_of` их
восстанавливает.

Цена: ~30 байт на версию (ссылки и номер) и 16 байт на цепочку в индексе.

## Операции

| Операция | Что делает |
|---|---|
| `remember` | записать эпизод, сущности и факты одной транзакцией |
| `recall` | найти факты: сущности, слова, окно времени, `as_of`, лимит; с объяснениями |
| `update` | закрыть факт и открыть новый, с причиной |
| `history` | цепочка версий факта или факты сущности по времени |
| `get` | конкретная версия по id или текущая по `lineage` |

## Запись и каналы поиска

**Запись синхронная** (см. компромисс К1):

```
remember ─► эмбеддинг (снаружи, до блокировки, если канал смысла включён)
         ─► коммит под блокировкой писателя:
               журнал (номер записи) + все индексы сразу
         ─► факт виден во всех каналах одновременно
```

**Каналы:**

| Канал | Что индексируем | Структура | Когда |
|---|---|---|---|
| Сущности | сущности факта | сущность → факты; синоним → сущность | M1 |
| Ключевые слова | слова текста | обратный индекс для BM25 | M1 |
| Время | время события, срок действия | не отдельный канал: фильтр по сроку действия и `as_of`, бонус за окно | M1 |
| Смысл | эмбеддинг (считается снаружи) | плоский массив int8 из HGVL, перебор | M4 |
| Связи | общие сущности, эпизод, связи сущностей | смежность | после замеров |
| Выученные ассоциации | совместное использование (журнал обращений) | веса связей | потом |

**Поиск:** каналы дают кандидатов → слияние по местам (RRF: баллы
каналов несравнимы, места сравнимы) → фильтр по сроку действия или
`as_of` → одна функция `rank` → результат с пометкой «кем найден».
Вес каналов настраивается; единой формулы может не быть (урок HGVL).
Модель-потребитель канал не выбирает: один вызов `recall`, движок сам
опрашивает каналы и сливает результат. **Новый канал добавляется, только
если замер показывает, что он чинит промахи остальных.**

|---|---|---|---|

## Хранение

- Данные в памяти, журнал на диске: JSON Lines с номером и контрольной
  суммой в каждой строке. Недописанный хвост при восстановлении
  отбрасывается. Индексы — производные, пересобираются из журнала.
- Один писатель, много читателей.
- Данными владеет один процесс-демон; файл-замок не даёт запустить
  второй.
- Журнал обращений (кто, что, когда доставал) — отдельный файл.

## Конкурентность

Пишут одновременно: несколько сессий Claude Code, команда агентов —
в рабочую память и в память проекта. Все ходят в один демон; данными
владеет только он (файл-замок не даст второму процессу открыть те же
данные). Защита в три слоя:

| Слой | Что ломается без него | Как | Цена |
|---|---|---|---|
| Физический | записи перемешались; два факта получили один id | один мьютекс на запись: под ним id = длина вектора, журнал и индексы обновляются вместе | один захват блокировки на транзакцию |
| Идентичность | две сущности «Аня» созданы одновременно | `get_or_create` по уникальному индексу ключей под тем же мьютексом | поиск в хеш-таблице |
| Смысл | агенты A и B прочитали версию 3; A записал 4, B записал «свою 4» поверх, не зная об A — изменение A потеряно | оптимистическая проверка версии: `update(lineage, expected: 3, …)`; если текущая не 3 — ошибка `Conflict` с текущей версией, агент перечитывает и решает | сравнение двух чисел |

Повторная запись факта, совпадающего с текущей версией, ничего не создаёт
и возвращает существующий id.

Атомарный счётчик id без мьютекса закрыл бы только первый слой: id были
бы разными, но агенты всё так же перезаписывали бы друг друга.

## Тепло и забывание

Память не должна расти бесконечно в горячей части, но и самоусиливаться
не должна: если часто вспоминаемое вспоминается ещё чаще, несколько
«сетей» вытесняют всё остальное.

- **Тепло — только для удержания, никогда для ранжирования.** Оно решает,
  что может остыть и уйти из горячей памяти, но не поднимает факты
  в выдаче.
- **Забыть = уйти из горячей памяти**: не подкладывается автоматически,
  не держится в индексах в RAM, но остаётся на диске и находится явным
  запросом («вспомнить старое»). Принцип «ничего не удаляется» сохраняется;
  настоящее удаление (приватность) — отдельная явная операция, потом.
- **Тепло растёт только от полезности, не от показов.** Иначе показы сами
  разгоняют тепло. Шкала оценки: −1 мимо, 0 показан без пользы, 1 полезно,
  2 бинго. «Мимо» относится к паре (запрос, факт) — это сигнал для
  настройки ранжирования и данные для набора оценки, а не повод остудить
  факт, который важен в другом контексте.
- **Угасает экспоненциально** с полураспадом (параметр).
- **Хранится не в факте:** побочная таблица по `lineage`, пересобираемая
  из журнала обращений. Содержимое факта неизменно, а чтение не должно
  превращаться в запись в основной журнал.

Откуда брать оценки, от дешёвого к дорогому:
1. **Бесплатные сигналы:** явный `get`/`recall` конкретного факта;
   ссылка на факт в ответе (хук `Stop` сравнивает ответ с выданными
   фактами); обновление или подтверждение факта.
2. **Редкая явная оценка агентом:** только «бинго» и «мимо», разреженно
   (`{8: 2, 1: -1}`) — 10–20 токенов вывода. Дороже токенов — лишний шаг
   модели, если это отдельный вызов инструмента; поэтому не на каждой
   реплике.
3. **Офлайн-судья:** дешёвая модель в фоне («сон») оценивает выданное по
   транскриптам, без задержки в основном цикле.

В модели уже есть типы `Heat` (значение и время, угасание) и `Usefulness`
(шкала −1..2, тепло дают только 1 и 2). Как и когда их применять —
решается после замеров.

### Контекстный приоритет: «индекс теплоты» проекта

Глобальное тепло — только удержание. Отдельно — **полезность в контексте
проекта**: для пары (проект, `lineage`) считаем, сколько раз факт показан
и насколько был полезен. Работая над проектом, демон держит эту таблицу
в памяти и мягко поднимает факты, которые в этом проекте обычно
пригождаются (например, правила пользователя о коммитах — да,
календарь — нет). Хранится в демоне, не в модели; ~16 байт на пару.

Риски — те же петли самоусиления, что в рекомендательных системах:
показанное чаще получает больше шансов на оценку; новое и непоказанное
не может подняться; приоритеты устаревают со сменой фазы проекта;
модель оценивает в пользу того, что сама процитировала.

Защиты:
- **только переранжирование кандидатов**, никогда не источник кандидатов:
  нерелевантный факт приоритет не вытащит;
- **ограниченный множитель** (например, ±20%): совпадение по сущности
  и словам всегда важнее;
- **доля, а не счётчик:** полезность / показы со сглаживанием — часто
  показанное, но бесполезное опускается, редко показанное не наказано;
- **исследование:** бонус за малое число показов (в духе UCB,
  детерминированно) — новое получает шанс;
- **угасание** с полураспадом — приоритеты следуют за фазой проекта;
- **новые и обновлённые факты** начинают с нейтрального приоритета,
  обновление наследует статистику цепочки;
- **только для автоматической подкладки** (бюджет мал, выбор важен);
  явный `recall` отдаёт чистую релевантность — смещение всегда можно
  обойти;
- **замер с ограждением:** с приоритетом и без на своих сессиях,
  плюс разнообразие выдачи (сколько разных фактов показано, насколько
  неравномерно) — если разнообразие падает, приоритет вредит.

## Интерфейсы

- Rust-библиотека — ядро.
- MCP-сервер в демоне (`rmcp`, HTTP на localhost): `remember`, `recall`,
  `update`, `history`.
- Хуки Claude Code: `SessionStart` (в том числе после компакта) —
  выжимка о пользователе и проекте; `UserPromptSubmit` — подкладка
  релевантной памяти на каждое сообщение.
- Потом: HTTP-сервис, Python-API (PyO3 + `.pyi`), голосовой агент.

## Глобальная память и области видимости

Память одна на компьютер: `~/.tessar/`, один демон на пользователя.
Любая сессия в любом проекте подключается к нему.

- **Пространства:** по одному на проект, плюс пространство пользователя
  (факты о человеке: предпочтения, правила — общие для всех проектов),
  плюс рабочие пространства команд.
- **Пространства — не стены, а «где лежит» плюс близость.** Запись
  всегда идёт в конкретное пространство (порядок и владение). Чтение —
  по всем пространствам сразу, но с весом близости: свой проект,
  пространство пользователя и рабочее пространство своей команды — 1.0,
  другие проекты — меньше.
- **Прорыв при сильной связи** (как тоннели в HGVL, только между
  пространствами): результат из далёкого пространства попадает в выдачу,
  только если сигнал сильный. В v0 — точное совпадение сущности
  по ключу или синониму либо сильное совпадение по словам; позже —
  векторы и выученные ассоциации. Каждый такой результат помечен:
  «из проекта cortex-db, прорыв по сущности HGVL».
- **Жёсткая стена** — только у пространств, явно помеченных закрытыми.
- **Память приходит сама, модель не нужно направлять:**
  - хук `SessionStart` — выжимка о пользователе и проекте;
  - хук `UserPromptSubmit` — на каждое сообщение пользователя `recall`
    по его тексту; в контекст попадает только прошедшее порог, в жёстком
    бюджете токенов, без повторов уже показанного в этой сессии;
  - инструмент `recall` остаётся для осознанного глубокого поиска.
- Календарь и подобное — события (`Event`) в пространстве пользователя;
  импорт через коннекторы — потом.
- **Как демон узнаёт проект сессии:** Claude Code запускает тонкий
  stdio-посредник `tessar mcp` в папке проекта; посредник знает свою
  рабочую папку и передаёт её демону. Агенту не нужно помнить, где он.
- **Сущности** живут в одном пространстве. Одинаковые «Rust» в двух
  проектах — разные сущности; поиск по всем проектам находит обе по
  ключу. Общие сущности (люди, технологии) в пространстве пользователя —
  открытый вопрос.
- Глобальная память делает демон и мьютекс обязательными: две сессии
  в разных проектах пишут одновременно в одно хранилище.

## Пространства и рабочая память команды

Строится потом, но модель учитывает сейчас. Рабочая память — общая
«доска» команды агентов на время одного воркфлоу:
- рабочее пространство — дочернее к пространству проекта;
- агенты читают насквозь (рабочее + проект), пишут только в рабочее;
- по окончании пространство архивируется (не удаляется), ценное
  поднимается в проект операцией `promote` с пометкой, откуда пришло.

## Этапы

**M1 — Ядро.** Модель данных, журнал, восстановление, каналы сущностей
и слов, время как фильтр и бонус, правило обновления, `as_of`, `recall`
с объяснениями.
*Выход:* случайные последовательности операций совпадают с наивной
моделью; обрезанный журнал не ломает загрузку; обновление создаёт
версию, ссылки `prev`/`next` и `lineage` согласованы; `as_of` возвращает
прошлое; исправление не попадает в «что было верно»; параллельные
писатели не дают повторных id и сущностей, конфликт версий ловится.

**M2 — LongMemEval.** Стенд (из HGVL), запись через LLM «как агент»,
базовые линии. *Выход:* решение по H1–H4 в точке решения.

**M3 — MCP и Claude Code.** Демон, MCP, хук компакта, golden-набор.
*Выход:* память о проекте tessar перенесена из markdown; цифры по H5, H6.

**M4 — Смысл.** Векторный канал (HGVL), слияние, замеры с отключением
каналов (H7).

**M5 — Голосовой агент.** Память между звонками и состояние диалога
в бюджете задержки; демо с ElevenAgents через MCP или webhook.

**Потом:** рабочая память команды, обучаемый слой ранжирования, связи
и PPR (если обгонят индекс сущностей), HTTP-сервис, Python-API.

## Уроки HGVL (cortex-db-rs)

- Иерархия обобщений не помогла и съедала бюджет контекста.
- Связи по сущностям и время помогли; простой индекс обогнал обход графа.
- Память ломается на обновлениях и времени, а не на похожести текста.
- Скорость не была риском; риск — качество и путь записи.
- Метод проверки (точка решения заранее, базовые линии, интервалы,
  честные отрицательные результаты) переносим целиком.

## Отложено

- Обучаемый слой ранжирования (теория комплементарных систем обучения:
  явная память — источник правды, обученное — слой поверх).
- Граф плана работ и UI наблюдения.
- Оркестратор и исполнитель — отдельный проект; пользуется рабочей
  памятью как доской.
- MVCC, язык запросов, хранение больше RAM.

## Открытые вопросы

- Один журнал на всё хранилище или по журналу на пространство
  (загружать только нужные). В v0 — один; у каждого события есть
  пространство, разделить можно потом.
- Общие сущности в пространстве пользователя и ссылки на них из проектов.
- Закрытые пространства, которые нельзя читать из других проектов.
- Тепло: полураспад, порог ухода в архив, закреплённые факты, которые
  не остывают (правила пользователя, ключевые решения).
- Однозначные предикаты: предварительно — схема у пространства
  (`define_predicate`), по умолчанию предикат многозначный.
- Модель эмбеддингов для M4.
