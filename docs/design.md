# graff — движок памяти для агентов

Рабочее имя, поменяется. Версия от 2026-11-07. Предыдущие версии
документа (граф плана, оркестратор, графовая БД общего назначения) —
в истории git. Отложенные из них идеи перечислены в конце.

## Зачем

- После компакта агент теряет состояние работы. Чтобы вернуть его,
  уходит 20–40% полезного окна.
- Память агентов в markdown-файлах затирает историю. Пример: запись
  «цель проекта graff» за два дня переписана трижды, старые версии
  пропали. А это ровно тот случай, когда нужно знать, что было верно
  раньше и почему поменялось.
- Готовые продукты памяти (Mem0, Graphiti, Cognee) — Python-надстройки
  над чужими базами. Нужно ядро на Rust: быстрое, типизированное,
  детерминированное, встраиваемое, позже — отдельный сервис.

Потребители по порядку:
1. **Claude Code** (пользователь и агент) через MCP — первый,
   ежедневный, на настоящих данных.
2. **Голосовой агент** — витрина: память между звонками и состояние
   диалога в бюджете задержки голоса.
3. **Другие агенты** через сервис — потом.

## Принципы

1. **Ядро без LLM.** Детерминированное: один запрос — один ответ.
   Извлечение фактов из текста — снаружи ядра и подключается.
2. **Ничего не удаляется.** У факта есть срок действия. Обновление
   закрывает старый факт и открывает новый. Любое чтение можно сделать
   «на момент T».
3. **Точные ключи прежде векторов.** Урок HGVL: связи по сущностям
   и время дали выигрыш, а обход графа проиграл простому индексу
   «сущность → упоминания».
4. **Каждый результат объясним:** по какой сущности, времени или слову
   он найден.
5. **Пространства памяти с первого дня.** Всё принадлежит пространству
   (`space`): пользователю, агенту, проекту. Без этого переход
   к сервису — переделка.
6. **Без замеров нет фич.**

## Модель данных

| Сущность | Поля | Зачем |
|---|---|---|
| `Space` | id, имя | граница данных: проект, пользователь, агент |
| `Entity` | id, тип (строка: `person`, `project`, `file`…), ключ, синонимы | точка входа в память; ключ уникален в пределах пространства и типа |
| `Episode` | id, текст, время, источник | исходный текст, из которого взяты факты: сообщение, сессия, документ |
| `Fact` | id, текст, упомянутые сущности, `subject`/`predicate`/`object` (необязательно), эпизод, время записи, время события, `valid_from`/`valid_to`, `superseded_by`, происхождение и уверенность | единица памяти |

**Правило обновления.**
- Если у факта есть структура `(subject, predicate)` и предикат
  однозначный («живёт в», «цель проекта»), новый факт с той же парой
  автоматически закрывает старый: `valid_to` = время нового,
  `superseded_by` = новый.
- Факты без структуры закрываются явно операцией `update`.

**Происхождение:** `asserted` — записал человек, агент или хук;
`inferred` — вывела модель или алгоритм, с уверенностью `0..1`.
Выведенное — гипотеза, пока не подтверждено.

## Операции ядра

| Операция | Что делает |
|---|---|
| `remember` | записать эпизод, сущности и факты одной транзакцией |
| `recall` | найти факты по запросу: сущности, слова, окно времени, `as_of`, лимит; вернуть с объяснениями |
| `update` | закрыть факт и открыть новый, с причиной |
| `history` | история сущности или факта: что когда было верно |

**Поиск v0:**
1. Сущности запроса: точное совпадение по ключу или синониму.
2. Кандидаты: факты, где упомянуты эти сущности, плюс совпадение
   по словам. Действующие сейчас или на момент `as_of`.
3. Бонус за окно времени — бонус, а не фильтр (урок HGVL: жёсткий
   фильтр вредил).
4. Одна функция `rank` с раздельными слагаемыми, детерминированный
   порядок при равенстве.

Поиск по смыслу (int8-векторы из HGVL) — в M4.

## Хранение

- Данные в памяти, журнал на диске. Журнал только дописывается:
  JSON Lines с контрольной суммой в каждой строке, `fsync` на каждый
  коммит. Недописанный хвост при восстановлении отбрасывается.
- Контрольные точки — когда проигрывание журнала станет заметно
  медленным.
- Один писатель, много читателей.
- Данными владеет один процесс-демон. Файл-замок не даёт запустить
  второй.
- Журнал обращений (кто, что, когда доставал) — отдельный файл.
  Он нужен для метрик и для обучаемого ранжирования потом.

## Интерфейсы

- **Rust-библиотека** — само ядро.
- **MCP-сервер** в том же демоне (`rmcp`, HTTP на localhost):
  инструменты `remember`, `recall`, `update`, `history`.
- **Хук Claude Code** `SessionStart` с matcher `compact`: подкладывает
  короткую выжимку действующих фактов проекта.
- **Потом:** HTTP-сервис для многих пользователей, Python-API
  (PyO3 + `.pyi`), голосовой агент.

**Извлечение для первого потребителя не нужно.** В Claude Code LLM уже
в цикле: агент сам вызывает `remember` со структурированными фактами
и сущностями. Конвейер извлечения из сырых диалогов нужен только для
голоса и наборов данных (M4).

## Оценка

- **Свой набор** из реальных сессий: «какая сейчас цель проекта» (должна
  вернуться последняя версия с историей), «что решили про HGVL», «почему
  отказались от X». Хранится как golden-тесты.
- **LongMemEval**, особенно трудные категории: knowledge-update,
  temporal-reasoning, multi-session. На них HGVL держал 63–87%. Стенд
  берём из HGVL.
- **Метрики:**
  - полнота top-k;
  - верность текущего значения для обновлённых фактов;
  - задержка p50 и p95;
  - сколько токенов уходит в контекст.

## Этапы

**M1 — Ядро.** Модель данных, журнал, восстановление, индекс сущностей,
сроки действия и правило обновления, `as_of`, `recall` v0 с объяснениями.
*Выход:* тесты:
- случайные последовательности операций совпадают с наивной моделью;
- обрезанный хвост журнала не ломает загрузку;
- обновление закрывает старый факт, `as_of` возвращает прошлое.

**M2 — MCP и Claude Code.** Демон, MCP-сервер, подключение.
*Выход:* память о проекте graff перенесена из markdown, агент
пользуется ею в сессиях; собираются случаи для набора оценки.

**M3 — Замеры и компакт.** Свой набор оценки, метрики, хук компакта.
*Выход:* цифры: полнота, верность текущего значения, токены после
компакта до и после.

**M4 — Смысл и извлечение.** Векторный поиск из HGVL, конвейер
извлечения через LLM, прогон на LongMemEval по трудным категориям.

**M5 — Голосовой агент.** Память между звонками и состояние диалога
(быстрое переписывание запроса) в бюджете задержки; демо
с ElevenAgents через MCP или webhook.

## Уроки HGVL (cortex-db-rs)

- Иерархия обобщений не помогла и съедала бюджет контекста.
- Связи по сущностям и время помогли; простой индекс обогнал обход
  графа.
- Память ломается на обновлениях и времени (knowledge-update,
  temporal-reasoning), а не на похожести текста.
- Скорость не была риском; риск — качество и путь записи.
- Метод проверки (точка решения заранее, базовые линии, интервалы,
  честные отрицательные результаты) — переносим целиком.

## Отложено

- Обучаемый слой ранжирования (веса из журнала обращений, онлайн-
  переранжирование) — по теории комплементарных систем обучения: явная
  память — источник правды, обученное — слой поверх.
- Обход графа и PPR (HippoRAG) — только если обгонят индекс сущностей
  на замерах.
- Граф плана работ и UI наблюдения.
- Оркестратор и исполнитель — отдельный проект на общем журнале.
- MVCC, язык запросов, хранение больше RAM.

## Открытые вопросы

- Имя проекта.
- Где лежат данные: глобально (`~/.graff/`) с пространствами
  по проектам или в каждом проекте.
- Однозначные предикаты: фиксированный список, объявление в схеме
  пространства или флаг в самом факте.
- Модель эмбеддингов для M4.
