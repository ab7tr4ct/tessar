# graff — дизайн

Рабочее имя, может поменяться. Документ фиксирует решения из обсуждения
дизайна (2026-11-05), чтобы контекст не терялся между сессиями.

## Задача

Разработка с агентами (Claude Code: оркестратор и субагенты) упирается
в контекст:

- после компакта агент теряет состояние работы: этапы, архитектуру,
  принятые решения;
- чтобы вернуть его, приходится заново скармливать всё это, и на это
  уходит 20–40% полезного окна;
- оркестратор тащит в своём контексте детали, которые нужны только
  воркерам.

graff — это граф, где лежат архитектура, решения, план и история работы.
Агенты достают из него только нужное и отбрасывают ненужное. Делается
в первую очередь для себя.

## Принципы

1. **Граф — источник правды, контекст — его кэш.** Компакт теряет детали,
   потому что модель пересказывает чат. Если состояние записано в граф
   по структуре, компакт перестаёт быть проблемой: брифинг собирается
   из графа программой, а не пересказом.
2. **Структура берётся из процесса, а не из текста.** Задача зависит от
   задачи, задача трогала файл, решение касается компонента: эти связи
   известны точно, их не нужно угадывать. Извлечение связей из свободного
   текста — самая трудная часть (вывод HGVL), её держим на втором плане.
3. **Точная и ассоциативная память в одном графе.** Решения, план,
   контракты и архитектура — точные: не угасают, не объединяются
   автоматически. Заметки, находки, связи, выведенные моделью, —
   ассоциативные: у них есть вес, уверенность, угасание. Разница —
   в атрибутах узлов и рёбер, а не в разных хранилищах.
4. **Ничего не удаляется.** Журнал только дописывается. Удаление — это
   пометка «снято». Отсюда бесплатно: состояние на момент T, разница
   версий плана, «почему мы свернули сюда».
5. **Забыть — значит опустить в выдаче, а не стереть.** Угасание влияет
   только на ранжирование.
6. **Выведенное моделью — гипотеза, пока не подтверждено.** Иначе память
   засоряется правдоподобными выдумками.
7. **Без измерений нет фич.** Каждая «умная» функция (веса, кластеры,
   консолидация) добавляется только с метрикой, которая показывает пользу.

## Архитектура: одно ядро, один граф

Один граф и одно пространство ID для всех доменов. Воркфлоу и память —
это две **схемы** (наборы типов узлов и рёбер с правилами) поверх одного
ядра, а не два графа.

Почему не два графа с коннекторами: пришлось бы изобретать общие ID,
синхронизацию, согласованность и связи между хранилищами. В одном графе
коннектор — это обычное ребро. Ассоциации между доменами идут через
**общие сущности**: узел `File "src/store/log.rs"` — один и тот же для
задачи, которая его трогала, и для заметки, которая его упоминает.

Раздельными остаются только **производные** данные: снимки для алгоритмов,
векторный индекс, кластеры. Их всегда можно пересобрать из журнала.

```
              ┌──────────────── схемы (правила, словари) ────────────────┐
              │  flow: Task, Decision, Run, Step…   memory: Passage, Entity… │
              └───────────────▲──────────────────────────▲─────────────────┘
                              │ валидация                 │ валидация
┌─────────────────────────────┴──────────────────────────┴───────────────┐
│ core: узлы, рёбра, свойства · журнал · восстановление · индекс ключей  │  ← источник правды
│       · смежность · версии во времени                                  │
└─────────────────────────────┬──────────────────────────────────────────┘
                              │ сборка снимка на версии V (с фильтром)
┌─────────────────────────────▼──────────────────────────────────────────┐
│ snapshot: неизменяемый CSR · обход с лучом · PPR · сообщества ·        │  ← производное
│           векторный поиск (int8, из HGVL)                              │
└────────────────────────────────────────────────────────────────────────┘
```

Это как OLTP и аналитика над одними данными: живое хранилище принимает
частые мелкие записи (план меняется постоянно), а тяжёлые алгоритмы
работают по неизменяемому снимку. Снимок HGVL как раз так устроен,
поэтому его код переиспользуется здесь.

### core — модель данных

| Что | Как |
|---|---|
| `NodeId`, `EdgeId` | `u64`, выдаются по порядку при записи в журнал |
| Тип узла и ребра | строка, при загрузке превращается в число (`KindId`); ядро типы не знает, их задают схемы |
| Ключ узла | необязательный, уникален в пределах типа: `File "src/main.rs"`, `Component "store"`. Индекс «тип + ключ → узел» — главный способ найти сущность (урок HGVL) |
| Свойства | словарь `имя → Value` (`Bool`, `Int`, `Float`, `Str`, `Time`); длинный текст — свойство `body`, краткое — `summary` |
| Ребро | направленное, `from`, `to`, тип, свойства; обратный обход — через обратную смежность, а не через автоматические обратные рёбра |
| Вес ребра | `f32`, по умолчанию 1.0 |
| Происхождение | `asserted` (записал агент, человек или хук) или `inferred` (вывела модель или алгоритм) с уверенностью `0..1` |
| Время | у каждого события в журнале — номер и время записи; у узла может быть `event_time` (когда это случилось на самом деле) |
| Снятие | событие `retire`, узел или ребро остаются в истории |

Журнал — последовательность событий: `create_node`, `set_props`,
`create_edge`, `retire`. Состояние — результат проигрывания журнала.
Состояние на момент T — проигрывание до T.

- Формат на старте: JSON Lines с контрольной суммой в каждой строке.
  Недописанная последняя строка при восстановлении отбрасывается.
  Бинарный формат — потом, если понадобится.
- Один писатель, много читателей.
- Ядро не знает ни про LLM, ни про эмбеддинги, ни про задачи. Оно хранит
  числа, строки и связи.

### Обход и фильтры

Любой обход и сборка снимка принимают фильтр: какие типы рёбер и какое
происхождение разрешены. Это защищает точную память от шума:
- запрос воркфлоу идёт только по рёбрам воркфлоу;
- поиск по памяти может заходить в узлы воркфлоу через общие сущности,
  если это разрешено.

### Журнал обращений

Каждое чтение через MCP (кто, в рамках какой задачи, какие узлы)
пишется в **отдельный** журнал, а не в основной. Это не правда о мире,
а данные о том, как память используется. Отсюда потом:
- метрики (см. ниже);
- веса связей («эти узлы часто достают вместе»);
- угасание по давности и частоте (ACT-R).

## Схема flow — план и история работы

| Тип узла | Что это |
|---|---|
| `Project`, `Component`, `Interface` | архитектура: карта, которую знает оркестратор |
| `Task` | узел плана |
| `DecisionPoint` | развилка: путь зависит от решения |
| `Decision` | что решили, почему, какие были альтернативы |
| `Question` | открытый вопрос |
| `Run`, `Step` | запуск агента и его шаги |
| `Report` | отчёт воркера по задаче |
| `File` | файл в репозитории (общая сущность) |

Рёбра: `DEPENDS_ON`, `PART_OF`, `AFFECTS`, `TOUCHES`, `PRODUCED_BY`,
`SUPERSEDES`, `CHOSE`, `ANSWERS`.

Статусы задачи: `planned` → `ready` → `running` → `done` | `failed`, плюс
`discarded` (ветку развилки не выбрали) и `superseded` (задачу заменили
при перепланировании). Переходы проверяет схема, ядро про них не знает.

```
[done] схема ─► [done] журнал ─► [running] MCP-сервер ─► ◇ UI на чём?
                                                  ├─► [planned] веб-UI
                                                  └─► [discarded] TUI
```

Перепланирование создаёт новые узлы и рёбра `SUPERSEDES` к старым.
Старые остаются, поэтому видно, как менялся план.

## Схема memory — ассоциативная память (в духе HippoRAG)

| Тип узла | Что это |
|---|---|
| `Passage` | кусок текста: заметка, тело отчёта, раздел документа |
| `Entity` | понятие или имя, упомянутое в текстах |

Рёбра: `MENTIONS` (`Passage → Entity`), `RELATED` (между сущностями,
выведено из текста), `SYNONYM` (выведено по сходству эмбеддингов).
Все выведенные рёбра — `inferred` с уверенностью.

Поиск, как в HippoRAG:
1. найти сущности запроса: точно по ключу, затем по векторам;
2. запустить Personalized PageRank от них по снимку;
3. ранжировать тексты по весам их сущностей.

Связь с flow: при извлечении сущностей упоминание сначала сопоставляется
с существующими узлами по ключу (пути файлов, имена компонентов). Тогда
память и план связаны точно, без угадывания.

Извлечение сущностей и связей делает LLM **вне ядра**, как обобщения
в HGVL.

## Протокол оркестратора и воркеров

Оркестратор не в неведении, а видит всё **на низком разрешении**: читает
`summary` и брифинг. Воркеры читают `body`.

1. Оркестратор ставит задачу: создаёт `Task`, связывает её
   с компонентами, решениями, файлами.
2. Воркер получает ID задачи и **пакет контекста**: соседей задачи на 1–2
   шага с фильтром по типам. Дальше при необходимости ищет сам.
3. В конце воркер пишет `Report` в граф: что сделал, какие решения принял,
   что осталось открытым. Оркестратору возвращает 3–5 строк.

**Брифинг** — документ ограниченного размера, который собирается из
графа программой: цель, план со статусами (только заголовки), последние
решения (заголовки), открытые вопросы, что сейчас выполняется. Размер
меряется (урок HGVL: обобщения в контексте съедали бюджет).

## Интеграция с Claude Code

Один процесс-демон `graff serve` владеет хранилищем:
- MCP по HTTP на localhost;
- веб-UI на том же сервере;
- хуки вызывают CLI `graff`, который ходит в демон.

Так несколько параллельных сессий Claude Code не пишут в один файл
одновременно.

MCP-инструменты (чем меньше, тем надёжнее ими пользуются):

| Инструмент | Что делает |
|---|---|
| `briefing` | брифинг для оркестратора |
| `plan_update` | создать или изменить задачи, развилки, статусы |
| `task_context` | пакет контекста для задачи |
| `record` | записать решение, факт или вопрос |
| `task_report` | отчёт воркера по задаче |
| `search` | поиск: по ключу, по тексту, позже по смыслу |

Хуки:

| Хук | Что делает |
|---|---|
| `SessionStart`, matcher `compact` | подкладывает брифинг после компакта |
| `PostToolUse` на `Edit`/`Write` | записывает ребро `TOUCHES` от текущей задачи к файлу |
| `SubagentStop` | проверяет, что воркер оставил отчёт |

Хуки важнее инструкций агентам: то, что собирается автоматически,
не зависит от того, не забыл ли агент что-то записать.

## Наблюдаемость

Веб-UI в демоне:
- граф плана в реальном времени: статусы, развилки, отброшенные ветки;
- таймлайн событий;
- клик по узлу показывает детали и историю;
- план на момент T и разница версий;
- журнал обращений: кто что доставал.

## Уроки HGVL (cortex-db-rs)

Из оценок на LongMemEval и BABILong (октябрь 2026):

- Иерархия обобщений не помогла найти нужное, а обобщения в контексте
  съедали бюджет. → Сводки здесь — инструмент бюджета оркестратора,
  и их размер меряется.
- Связи по сущностям и время помогли: +59…+80 п.п. на BABILong,
  +7,8 п.п. на LongMemEval при 2 тыс. токенов. → Индекс «сущность →
  упоминания» и время — основные способы войти в память.
- Простой двухшаговый поиск без графа обогнал обход графа на 128k.
  → Сложный обход и PPR добавляются только поверх точного индекса
  и только с замером.
- Единой формулы ранжирования нет. → Ранжирование настраивается под тип
  запроса и проверяется на разных данных.
- Детерминизм, golden-тесты, кэш ответов LLM, доверительные интервалы —
  культура проверки, которую переносим.

Код: модули поиска по векторам (int8), CSR и обхода переиспользуются
в `snapshot`. Нужны обобщения: типы рёбер не фиксированный `enum`,
у рёбер вес.

## Метрики

| Что | Как меряем |
|---|---|
| Цена восстановления контекста | токены, которые уходят после компакта до продолжения работы: до graff и с ним |
| Размер брифинга | токены брифинга при разном размере проекта |
| Повторные чтения | сколько раз воркер читает файлы, уже описанные в пакете контекста |
| Промахи памяти | сколько раз агент ищет или спрашивает то, что уже есть в графе |
| Качество поиска по памяти | recall@k на своих сессиях, позже на MuSiQue/2Wiki в постановке HippoRAG |

Первые четыре считаются по журналу обращений и транскриптам сессий.

## Этапы

Каждый этап заканчивается проверяемым критерием выхода.

**M1 — Ядро.** Модель данных, журнал, восстановление, индекс ключей,
смежность, состояние на момент T, фильтры обхода.
*Выход:* тесты: проигрывание журнала даёт то же состояние; недописанный
хвост журнала не ломает загрузку; состояние на момент T верно;
случайные последовательности операций совпадают с наивной моделью.

**M2 — Схема flow и CLI.** Задачи, статусы, развилки, решения,
перепланирование, сборка брифинга.
*Выход:* план работ над graff ведётся в graff через CLI; размер брифинга
измерен.

**M3 — Демон, MCP и хуки.**
*Выход:* graff разрабатывается с помощью graff; цена восстановления
контекста после компакта измерена до и после.

**M4 — UI.** Граф плана в реальном времени, таймлайн, детали узла,
журнал обращений.

**M5 — Снимок и алгоритмы.** CSR из HGVL, обход с лучом, PPR, пакет
контекста по соседству в графе.

**M6 — Схема memory.** Тексты, сущности, извлечение вне ядра, поиск
через PPR, векторный поиск.
*Выход:* на своих сессиях поиск по памяти лучше поиска по тексту хотя бы
на заметную величину; иначе остаёмся на точном индексе.

**M7 — «Как мозг».** Веса из журнала обращений, угасание, кластеры
со сводками, фоновая консолидация, гипотезы новых связей. Каждая функция —
отдельно и только с метрикой из таблицы выше.

## Открытые вопросы

- Где хранить данные: в проекте (`.graff/`) или глобально
  (`~/.graff/`). Может быть, журнал проекта стоит держать в git —
  тогда история плана живёт рядом с кодом.
- HGVL: зависимость (путь или git) или копирование нужных модулей
  с переделкой API.
- Модель эмбеддингов для M6: локальная (bge-small, как в HGVL) или по API.
- Как хранить общие сущности, если проектов несколько.
- Имя проекта.
